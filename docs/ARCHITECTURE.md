# بنية النظام وخطة التطوير

## الحدود الرئيسية

المستودع يضم تطبيقين مستقلين، ولا ينبغي أن يتحول وجودهما في مستودع واحد إلى اعتماد تشغيلي بينهما:

1. **Flutter** يدير واجهات الجهاز والاتصال المحلي بـRouterOS، وبيانات التطبيق المخزنة محليًا.
2. **Telegram Bot** خدمة Python مستقلة تتصل مباشرة بواجهة RouterOS API، وتتحقق من هوية Chat والمستخدم قبل تمرير الأوامر.

لا يستدعي تطبيق Flutter خدمة البوت عبر `localhost`، ولا يشغّل البوت عمليات RouterOS عبر subprocess أو طبقة ترحيل غير لازمة.

## Flutter

```text
lib/main.dart
  └── bootstrapApplication() → ApplicationRoot
       ├── ProviderScope + Provider (توافق الحالة القائمة)
       └── MyApp / MaterialApp
            ├── features/auth/presentation/login_screen.dart
            └── features/dashboard/presentation/
                 ├── home_screen.dart
                 └── dashboard_status_card.dart

lib/core/
  ├── app_bootstrap.dart       فتح Isar وترحيل البيانات وتسجيل فشل التهيئة
  ├── app_runtime.dart         مراجع الخدمات العامة المستقرة وScaffoldMessenger
  ├── navigation/              انتقالات التنقل المشتركة
  └── widgets/                 عناصر واجهة عامة
```

- `main.dart` مسؤول عن التهيئة ثم `runApp` فقط. يعيد تصدير أسماء عامة قديمة حتى لا تنكسر اختبارات التكامل أو الشاشات التي تعتمد على الواجهة السابقة أثناء الترحيل.
- `app.dart` هو **composition root**: يثبت `ProviderScope` ومزوّدي Provider القديمين و`MaterialApp` مرة واحدة.
- `app_bootstrap.dart` يفصل فتح قاعدة البيانات وترحيلها عن تركيب الواجهة. فشل ترحيل بيانات قديمة يُسجّل ولا يمنع فتح التطبيق، كما في السلوك السابق.
- `app_runtime.dart` يحتفظ بمراجع ثابتة. `IsarProvider` نفسه singleton، لذا استدعاء نقطة الدخول أكثر من مرة في الاختبارات لا يعيد إسناد `late final` أو يفتح مزودًا مختلفًا.
- `snackbar_helpers.dart` هو المصدر الوحيد لرسائل النجاح والخطأ؛ استُخدم بدل النسخ المتكررة في نقطة الدخول.
- استيراد `main.dart` من طبقات التخزين والخدمات أُزيل؛ تستخدم تلك الطبقات ملف الخدمة المحدد مباشرةً.

### حدود حالية وخطوات Flutter التالية

فصل الشاشتين عن نقطة الدخول خطوة تأسيسية وليس ادعاءً بأن كل التطبيق صار Clean Architecture. `LoginScreen` و`HomeScreen` ما زالتا كبيرتين، والاعتماد على Provider وRiverpod معًا قائم لأسباب توافق الشاشات.

#### تحسينات مسار اتصال RouterOS

- `MikrotikConnector.connect()` يشارك Future واحدًا خلال قراءة الإعدادات وفحص الاتصال والمصافحة؛ استبدل ذلك polling كل 100ms الذي كان قد ينتهي بخطأ بعد خمس ثوانٍ بينما مهلة الاتصال الفعلية 30 ثانية.
- فحص صحة العميل المخزن يحدث بعد فترة خمول، لا عند كل استعمال متقارب. تبقى مهلة 30 ثانية لدعم الشبكات البعيدة والبطيئة، ولا يُغلق اتصال جديد متأخر بعد `forceDisconnect()`.
- `services/router_os_query_executor.dart` يرسل الأوامر المتزامنة عبر `talkTagged` بوسوم فريدة؛ لا تُشغّل استدعاءات `talk` القديمة بلا tag بالتوازي على socket مشترك. تُجمع قراءات لوحات المعلومات المستقلة بالتوازي، وتبقى الخطوات المعتمدة على نتيجة سابقة — مثل اختيار الواجهة قبل مراقبة سرعتها — متتابعة.
- `v2/core/router_service.dart` صار واجهة توافق فوق `MikrotikConnector` بدل إنشاء socket وإعادة قراءة الاعتمادات بمنطق موازٍ.
- يوقف `SystemDashboardScreen` و`ActiveUsersScreen` مؤقتهما عند خمول التطبيق ويحدّثان البيانات عند العودة؛ تمنع الشاشتان أيضًا تداخل طلبات التحديث.

هذه تغييرات موضعية في المسار الساخن وليست بديلًا عن حقن repository أو نقل حالة الشاشات خارج Widgets. الخطوات التالية المناسبة، كلٌّ على حدة مع اختبارات سلوك قبل نقل المنطق، هي:

1. تقسيم `LoginScreen` إلى نموذج اتصال/إعداد اتصال محلي وعن بعد وVPN، وخدمات تخزين واعتماد مستقلّة.
2. استخراج حالة لوحة المعلومات وقراءات الراوتر إلى controller/provider واختبار تحديثها عند تغيّر دورة حياة التطبيق.
3. تحويل تدفق التنقل بين الدخول ولوحة المعلومات إلى اعتماد قابل للحقن، ثم تقليص تصديرات التوافق من `main.dart` بعد تحديث مستهلكيها.
4. توحيد إدارة الحالة في Riverpod **بعد** ترحيل مستهلكي Provider والتحقق من دورة حياة `MqttService` و`AppTheme`؛ لا تُحذف طبقة توافق لمجرد وجود مكتبتين.
5. تحديد عقود repositories ومهايئات RouterOS وIsar قبل نقل بيانات الإنتاج أو تغيير مخطط قاعدة البيانات.

لا ينبغي تحريك ملفات Isar المولدة أو إعادة توليدها ضمن نقل بنيوي عادي؛ تغيير مخططها يحتاج ترحيلًا واختبارات رجوع منفصلة.

## Telegram Bot

```text
telegram_bot/app.py
  ├── config.Settings + load_env_file
  ├── healthcheck.run_selftest
  └── runtime.BotRuntime
       ├── commands.CommandRouter → RouterOSOperations → RouterOSV6Client
       ├── polling.TelegramUpdatePoller → TelegramPolicy + OffsetStore
       ├── security.AuditTrail
       └── InternetMonitor + TrafficMonitor
```

- `app.py` واجهة CLI: تحميل الإعدادات، فحص الذات، إنشاء runtime، وتحويل أخطاء البدء إلى رمز خروج واضح.
- `runtime.py` يملك الاتصالات الثلاث المنفصلة (الأوامر، فحص الصحة، عدادات الحركة)، ويبدأ عمال المراقبة ويوقفهم ويغلق الاتصالات في `finally`. يظل الاتصال المنفصل لكل عامل مهمًا لأن كل عميل RouterOS يحتفظ بجلسة socket مستقلة.
- `polling.py` يعزل استقبال تحديثات Telegram والتحقق من هوية المستخدم/chat عن دورة حياة الخدمة. يُحفظ offset بكتابة ملف مؤقت في المجلد نفسه ثم `os.replace`، ويحدث بعد معالجة كل تحديث.
- التسليم هنا **at-least-once**: إذا اكتمل أمر ثم تعذر حفظ offset فقد يصل التحديث مجددًا. عمليات التغيير عالية الخطورة تستخدم تأكيدًا قصير العمر ومربوطًا بالمستخدم والمحادثة وسجل تدقيق؛ لا تدّعي البنية أن offset وحده يوفر exactly-once.
- حالات فشل الأمر أو callback تُحتوى لكل تحديث حتى لا تمنع بقية الدفعة، وفشل Telegram/RouterOS في دورة الاستقصاء يؤدي إلى إعادة المحاولة بعد مهلة الإعداد.
- أخطاء التشغيل تسجل نوع الخطأ بدل طباعة بيانات الاتصال أو محتوى الأسرار. يظل مستوى التسجيل قابلًا للضبط عبر `LOG_LEVEL`.

### ضمانات أمنية ينبغي عدم إضعافها أثناء التطوير

- السماح مشروط بهوية المستخدم **و** Chat ID، والعمليات المغيّرة تتطلب مجموعة المسؤولين والتأكيد.
- مسارات الأوامر المسماة فقط هي التي تصل إلى RouterOS؛ لا يُمرر مسار أوامر خام من رسالة Telegram.
- حقول User Manager تُقيد بقائمة عرض، وتُنقّى الأسرار قبل إرسالها.
- API-SSL على `8729` هو الافتراضي؛ HTTP API غير المشفر يحتاج استثناء تشغيل صريح.
- لا تُسجّل كلمات المرور أو Bot Token في التدقيق أو السجلات. ملفات البيئة والمفاتيح لا تُضاف إلى Git.

## قواعد تعديل البنية

1. ضع منطق المجال بعيدًا عن Widgets وعمليات I/O المباشرة متى أمكن؛ لا تنقل كودًا وتغيّر سلوكه في التغيير نفسه دون اختبار.
2. اجعل الاعتمادية اتجاهية: composition root يعتمد على الشاشات والخدمات؛ لا تستورد الشاشة نقطة الدخول أو composition root.
3. عند تغيير المفتاح/المخطط/الإعداد، أضف مسار ترحيل يحافظ على بيانات النسخة الحالية.
4. اختبر الأوامر التغييرية بـfake router أولًا، ولا تنفذ اختبارات حية على RouterOS الإنتاجي.
5. لا تحذف compatibility exports أو ملفات قديمة قبل فحص كل المستهلكين وتشغيل Flutter analyze والاختبارات على CI.
