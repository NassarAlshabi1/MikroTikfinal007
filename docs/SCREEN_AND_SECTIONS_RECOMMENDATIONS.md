# مقترحات تحسين الشاشات والأقسام وتجربة الاستخدام

## الهدف

تطوير تطبيق **MkCards / MikroNet** ليكون واضحاً وسريعاً في الاستخدام اليومي، مع التركيز على دورة العمل الأساسية:

> **إنشاء الكروت → بيع الكروت → متابعة التقارير**

يجب أن تحافظ جميع الشاشات على التصميم الداكن الحالي، وأن تعمل الوظائف الأساسية دون اتصال مستمر بالإنترنت أو الراوتر كلما كان ذلك ممكناً.

---

## مبادئ عامة

1. **Offline First**: قراءة البيانات المحلية وعرضها دون اتصال، ثم مزامنتها عند توفر الراوتر.
2. **وضوح الحالة**: إظهار متصل، غير متصل، آخر مزامنة، والعمليات المعلقة.
3. **إجراء سريع**: الوصول إلى العمليات اليومية خلال نقرتين أو أقل.
4. **منع فقدان البيانات**: حفظ العملية محلياً قبل إرسالها للراوتر، مع دعم الاستئناف وإعادة المحاولة.
5. **توحيد التصميم**: نفس الألوان، المسافات، أحجام الأزرار، حالات التحميل، ورسائل النجاح والخطأ.
6. **دعم الشاشات الصغيرة**: الواجهة الأساسية مصممة للهاتف، مع دعم أفضل للأجهزة اللوحية والوضع الأفقي.

# 1. الشاشة الرئيسية

## التصميم المقترح

تقسيم الشاشة إلى أربع مناطق:

### أ. حالة الشبكة والراوتر

- حالة الراوتر: متصل / غير متصل.
- عنوان الاتصال الفعلي، وليس عنواناً ثابتاً.
- إصدار RouterOS.
- مدة التشغيل.
- استخدام المعالج.
- استخدام الذاكرة.
- عدد المستخدمين النشطين.
- وقت آخر مزامنة ناجحة.
- زر تحديث يدوي متاح دائماً.

### ب. إحصاءات سريعة

بطاقات قابلة للضغط:

- إجمالي الكروت.
- الكروت المباعة.
- الكروت المتبقية.
- الكروت المنتهية.
- مبيعات اليوم.
- مبيعات الشهر.

### ج. الإجراءات السريعة

- إنشاء كرت واحد.
- إنشاء دفعة كروت.
- المستخدمون النشطون.
- بيع كرت.
- طباعة آخر دفعة.
- النسخ الاحتياطي.

### د. التنبيهات

- الراوتر غير متصل.
- ارتفاع استخدام المعالج.
- انخفاض مساحة التخزين.
- كروت فشلت إضافتها.
- وجود عملية معلقة.
- مرور فترة طويلة منذ آخر نسخة احتياطية.

## تحسينات تقنية

- المزامنة الدورية بفاصل زمني خفيف، مثل 60 ثانية.
- عدم تشغيل طلب جديد إذا كان طلب سابق ما زال قيد التنفيذ.
- فصل حالة اتصال الراوتر عن فشل استعلام واحد مثل المستخدمين النشطين.
- الاحتفاظ بآخر بيانات ناجحة عند انقطاع الاتصال.
- عدم عرض قيم ثابتة إذا كان بالإمكان قراءتها من إعدادات الاتصال أو قاعدة البيانات.

# 3. شاشة إنشاء دفعة الكروت

يفضل تنظيم الشاشة إلى خطوات واضحة بدلاً من عرض جميع الخيارات دفعة واحدة.

## الخطوة الأولى: مصدر الدفعة

- إنشاء جديد.
- استيراد من ملف.
- نسخ دفعة سابقة.
- إعادة توليد دفعة غير مكتملة.

## الخطوة الثانية: بيانات الدفعة

- اسم الدفعة.
- الباقة.
- قالب الطباعة.
- نقطة البيع.
- إظهار نقطة البيع على الكرت.

## الخطوة الثالثة: خيارات التوليد

### اسم المستخدم

- أرقام فقط.
- حروف فقط.
- حروف وأرقام.
- طول اسم المستخدم.
- بادئة اختيارية.
- لاحقة اختيارية.
- استبعاد رموز أو أحرف محددة.

### كلمة المرور

- اسم مستخدم فقط بدون كلمة مرور.
- كلمة مرور مختلفة لكل كرت.
- كلمة المرور مطابقة لاسم المستخدم.
- طول كلمة المرور.
- التحقق من توافق نوع كلمة المرور مع قالب الطباعة.

### العدد

- عدد الكروت.
- عدد الصفحات المتوقع.
- بداية التسلسل إن كانت مطلوبة.
- نهاية التسلسل إن كانت مطلوبة.

## الخطوة الرابعة: المعاينة

قبل الإرسال إلى الراوتر، عرض:

- أول 5 أو 10 كروت.
- أسماء المستخدمين.
- كلمات المرور إن كانت مفعلة.
- الباقة.
- القالب.
- نقطة البيع.
- العدد الإجمالي.
- عدد الصفحات.

الأزرار:

- إعادة التوليد.
- تعديل الخيارات.
- معاينة PDF.
- تأكيد الإنشاء.

## الخطوة الخامسة: التنفيذ

عرض تقدم واضح:

- تم إنشاء الدفعة محلياً.
- تم إرسال 100 من 765.
- نجح: 98.
- فشل: 2.
- متبقٍ: 665.

بعد الفشل، يجب توفير:

- إعادة إرسال الكروت الفاشلة.
- إيقاف العملية واستكمالها لاحقاً.
- عرض سبب الفشل.
- حذف الدفعة غير المكتملة.

# 13. التصميم وتجربة المستخدم

- توحيد ارتفاع البطاقات والأزرار.

  - أخضر: نجاح.

- دعم الوضع الأفقي للأجهزة اللوحية.
- ضبط أحجام النصوص العربية.
- توفير رسائل نجاح وخطأ قصيرة وواضحة.
- إضافة تأكيد قبل الحذف أو الاستعادة أو العمليات الجماعية.
- منع الأزرار من تغيير مكانها أثناء التحميل.

# 14. متطلبات العمل دون اتصال

## يجب أن تعمل دون اتصال

- فتح الشاشة الرئيسية.
- عرض آخر بيانات ناجحة.
- عرض الكروت المحلية.
- البحث والفلترة.
- عرض الدفعات السابقة.
- معاينة القوالب المحفوظة.
- إنشاء دفعة محلياً.
- إنشاء PDF من البيانات المحلية.
- إنشاء نسخة احتياطية محلية.
- عرض التقارير المحلية.

## تحتاج إلى اتصال عند التنفيذ

- إرسال الكروت إلى الراوتر.
- قراءة المستخدمين النشطين مباشرة.
- تعديل بيانات الراوتر.
- قطع جلسة مستخدم.
- اختبار الاتصال.
- رفع نسخة احتياطية إلى خدمة خارجية.

## السلوك عند عودة الاتصال

- مزامنة العمليات المعلقة.
- إعادة إرسال الكروت الفاشلة بعد موافقة المستخدم أو حسب إعداد اختياري.
- تحديث الإحصاءات.
- تسجيل وقت المزامنة.
- الاحتفاظ بسجل العمليات التي تمت بنجاح أو فشلت.

يجب تنزيل الخطوط والموارد المطلوبة ضمن التطبيق واستخدام مسارات محلية، وعدم اعتماد الواجهات الأساسية على CSS أو JavaScript أو خطوط خارجية.

# 15. خطة التنفيذ المقترحة

## المرحلة الأولى: أثر سريع

1. ربط إحصاءات الشاشة الرئيسية بالبيانات الحقيقية.
2. عرض عنوان الراوتر الفعلي ووقت آخر مزامنة.
3. إضافة البحث والفلترة في إدارة الكروت.
4. إضافة اسم الدفعة للمستخدم.
5. تحسين حالات التحميل والفراغ والخطأ.
6. إضافة معاينة قبل إنشاء الدفعة.

## المرحلة الثانية: العمليات اليومية

1. تطوير حالة التقدم أثناء إرسال الدفعة.
2. دعم إعادة إرسال الكروت الفاشلة.
3. تطوير شاشة المبيعات.
4. تطوير كشف حساب الموزعين.
5. تحسين الطباعة وإعادة الطباعة.

## المرحلة الثالثة: الاعتمادية والتوسع

1. دعم أكثر من راوتر.
2. نظام مزامنة محلي متكامل.
3. سجل تدقيق شامل.
4. نسخ احتياطي مجدول.
5. تقارير قابلة للتصدير.
6. اختبارات Controller وIntegration.
7. تحسين دعم الأجهزة اللوحية والوضع الأفقي.
